# benchmantic

benchmantic turns a simulation benchmark's source code into a standardized, machine-readable semantic description (`benchmark.jsonld`, RO-Crate 1.1 / metadata4ing), and packages a ready-to-run Snakemake workflow around it. It's used to prepare and validate benchmark entries for the NFDI4Ing Model Validation Platform and similar consumers.

Pipeline: **discover → infer → review → build → validate**. AI inference proposes parameter/metric metadata; a human reviews and can edit any field before it's built into the graph; corrections are remembered across benchmarks and fed back into future prompts.

## When to use this skill

Use this skill when the task involves any of:

- Extracting a semantic description (`benchmark.jsonld`) from a simulation model's source code or repository.
- Inferring units, quantity kinds, or semantic names for simulation parameters/metrics from source code context.
- Reviewing/editing AI-inferred metadata before it's committed to a benchmark description.
- Rendering an existing `benchmark.jsonld` as a human-readable Markdown table for review.
- Verifying that a generated description conforms to the `semantic_benchmark` schema/loader.
- Producing a packaged, container-runnable Snakefile workflow, including mesh-splitting options for rotating-cylinder-style benchmarks.
- Running the full describe → review → build → validate pipeline end-to-end, e.g. for CI (with `--skip-review`).

## Installation

```bash
git clone https://github.com/Simulation-Benchmarks/benchmantic.git
cd benchmantic
pip install groq rdflib
```

`groq` is the default LLM provider (free tier). To use OpenAI instead, `pip install openai` and pass `--provider openai` (plus `--model`, optionally). `rdflib` is needed for `verify_description.py`, which also needs a `semantic-benchmark` checkout:

```bash
git clone https://github.com/Simulation-Benchmarks/semantic-benchmark.git
```

(auto-detected as a sibling/child directory, or pass `--semantic-benchmark-src` / set `SEMANTIC_BENCHMARK_SRC`). `pip install pyyaml` too, only if you use `--config`.

## Quickstart

Run the full pipeline (generate, review, verify) in one command:

```bash
python3 workflow.py <module_dir> \
    --scenario-params Cells0,Cells1,Grading0,Radial0,Name,Omega1,Omega2 \
    --full-value-params Radial0 \
    --container-image <docker-image> \
    --container-shared-dir <host-mount-path> \
    --mesh-split --zip-name-flag Problem.Name
```

`<module_dir>` can be the exact benchmark folder, a repository checkout containing one, or a GitHub/GitLab/any git URL (e.g. `https://github.com/org/repo`, `git@host:org/repo.git`) — cloned into a throwaway temp directory deleted once the run finishes, by default; pass `--keep-clone` to clone into a persistent local cache reused across runs instead (along with its inference cache), `--ref` to pin a branch/tag/commit, `--clone-dir` to pick an explicit clone location (implies `--keep-clone`), or `--fresh-clone` to discard and re-clone an existing persistent one. This walks you through selecting parameters, choosing which artifacts to generate, and (unless you chose the **Workflow only** preset) reviewing the AI-inferred metadata (an arrow-key curses screen on a real terminal for each, falling back to plain-text prompts otherwise -- see the Select outputs and Infer & review steps below), writes whichever of the semantic description, its dataset-provenance sidecar, a plain `Snakefile` (no zip), and `review.md` were selected, to `outputs/<software-name>/`, and validates the result (skipped entirely for **Workflow only**, which produces just the Snakefile) — exiting non-zero if verification fails. Both jsonld filenames default to a slug of the benchmark's own name -- `<benchmark-name>_benchmark.jsonld` (parameters/metrics/processing steps) + `<benchmark-name>_dataset.jsonld` (author/publisher/dependencies), neither suffix doubled up if the name already contains that word -- pass `--benchmark-filename`/`--dataset-filename` to force specific names instead. Output stays short by default (checklist lines + a final boxed summary), announced as six numbered steps (`1/6` through `6/6`) regardless of verbosity -- pass `-v`/`--verbose` or `--debug` for progressively more detail. For CI/non-interactive use, add `--skip-review` (this and the Outputs step both need a real terminal to prompt; without one, both are skipped automatically) and `--outputs <preset-or-list>` to fix which artifacts get generated without being asked. Skip individual pipeline steps with `--skip-show` / `--skip-check`. Instead of retyping a benchmark's usual flag set every run, save it to YAML and pass `--config <path>` (both `workflow.py` and `describe_benchmark.py` accept it; a flag also given on the command line still overrides the same key in the file) -- see `config.py`'s docstring for the exact format.

## Step-by-step

`describe_benchmark.py` is the entry point and runs five stages in process -- on screen these map onto six numbered step banners (`1/6 Discover benchmark`, `2/6 Select parameters`, `3/6 Select outputs`, `4/6 Infer & review`, `5/6 Generate`, `6/6 Validate`), printed unconditionally as structural markers regardless of `--verbose`/`--debug`, since stage 1 below covers both discovery and parameter selection. Select outputs (`3/6`) deliberately comes BEFORE inference (`4/6`): it's the one decision (the **Workflow only** preset) that can skip semantic inference -- and its LLM call -- entirely, so it has to be made before that call, not right before generation. On a real terminal, the very first run also opens with a short "Press Enter to continue…" explanation screen (skipped automatically for non-interactive/CI runs, or on any later run once `--verbose`/`--debug` is in effect):

1. **Discover** (`metadata.repo_source`, `metadata.repository`, `metadata.parameters`, `metadata.metrics`) — resolves `module_dir` first: used as-is if it's a local path; a git URL is cloned into a throwaway temp directory, deleted automatically once the run finishes (or, with `--keep-clone`, into a persistent cache instead — default `.benchmantic_repo_cache/`, override with `BENCHMANTIC_REPO_CACHE` or `--clone-dir`). Then scans `params.input`, `main.cc`, `problem.hh`, `README`, and `CMakeLists.txt` for parameter/metric candidates, license, dependencies, build info, citation, and authors. Pass `--scenario-params` to select case-varying parameters non-interactively (required for unattended/CI runs — omitting it triggers an interactive prompt): on a real terminal that's a curses checklist (`↑`/`↓`/`j`/`k` move, `Space` toggles the highlighted row, or type any row's own number to jump the highlight straight to it, however far down a long list it is -- the highlight moves live with each digit you type, the digits themselves show on their own "Go to #: " line with a real visible cursor so you can always see what you've typed so far). On a wide terminal (100+ columns) with more than a dozen candidates, this is a two-column layout -- numbered straight down the left column then continuing down the right (1-19, then 20-38 for a 38-parameter benchmark) -- with a live "Selected N/total" badge and a running comma-separated list of exactly what's checked at the bottom; `Tab` (or `←`/`→`) hops the highlight to the matching row in the other column, everything else works the same as the single-column version. A shorter list or a narrower terminal stays single-column (scrolling to fit the terminal automatically) -- the same layout the Outputs step's own small "Custom" toggle screen always uses, since a mostly-empty second column for a handful of items would just look broken. Either way: Enter toggles the highlighted row, `a`/`n` select all/none, Enter with nothing typed finishes, `q`/Escape cancels to the plain-text fallback, which takes comma-separated index numbers / `all` / `none` / `table`, with its column count adapted to the terminal's width.
2. **Select outputs** (`metadata.builder._resolve_outputs_selection()`, `ai.tui.output_picker()`) — decides which artifacts this run actually produces. `--outputs <preset-or-list>`, if given, wins outright with no prompt. Otherwise, on a real terminal (and unless `--skip-review`): an info panel of cards is shown first, purely informational (no `[x]`/`[ ]` marks -- nothing on it is toggled from that screen) -- one card per artifact (Benchmark description, Dataset description, Reproducible workflow, Review report), each with its file-type badge (`JSON-LD`/`Snakefile`/`Markdown`) and a one-line purpose, laid out in as many columns as the terminal is wide enough for. Below that, on a wide-enough terminal (roughly 92+ columns and tall enough for every preset), a two-pane picker: presets (Standard / Workflow + Description / **Workflow only** / Description only / Description + Dataset / Custom, "Standard" marked `[Recommended]`) on the left, and a live "Preset preview" pane on the right that updates on every arrow keypress -- a ✓/✗ row per artifact with its actual filename (or `(skipped)`), plus the preset's own one-line summary -- so Enter always confirms something you've already seen in full; `metadata.builder` skips the separate plain-text `? Generate these files? [Y/n]` prompt entirely once this picker returns a selection, since the live preview already served that purpose. A narrower or shorter terminal falls back to the previous single-column preset menu instead (same card panel above it, each preset with its one-line description, or a per-artifact custom choice -- dataset sidecar and/or Snakefile, since the benchmark description and review report aren't Custom-toggleable, only reachable via **Workflow only**) -- that path still ends with the plain-text preview-and-confirm prompt (`n` reopens the picker, reseeded with the declined choice, rather than proceeding), since it has no live preview of its own. If the single-column menu's names plus wrapped descriptions don't all fit the terminal's current height, it scrolls -- the highlighted preset always stays on-screen as `↑`/`↓`/a digit move past the visible edge, with a "(more below)"/"(more above)" footer hint -- so a short terminal window means scrolling to a preset, never losing access to it. Otherwise (CI / `--skip-review` / no real terminal) the module's last saved choice is silently reused, or every artifact is generated on a module's very first run. Either way -- interactive picker, reused selection, `--outputs`, or the silent default -- a one-line summary prints right after resolution (`-> Standard -- Semantic description, dataset provenance, and Snakefile.`, naming the matching preset, or a plain list of what's included for a combination that doesn't match any named preset), so a non-interactive run isn't left with an unexplained gap between the `3/6`/`4/6` step banners. The resolved selection is persisted to `.benchmantic_outputs.json` beside the module (same convention as `.parameter_metadata_cache.json`), so a later run against the same module doesn't ask again unless `--outputs` overrides it. **Workflow only** is the one preset that skips the benchmark description, dataset sidecar, and review report AND the LLM call itself (step 3 below) -- no `GROQ_API_KEY`/`OPENAI_API_KEY` needed in that mode -- at the cost of a real limitation: since no unit is ever inferred, no parameter gets the usual unit-suffixed `parameters.json` key (see the Config files section of README.md, or `snakefile.renderer.config_key()`'s docstring), which matters if the actual `run_benchmark.py` your container runs expects a unit suffix for a parameter whose real unit is meters or pascals.
3. **Infer & review** (`ai.cache`, `ai.inference`, `ai.review`, `ai.tui`) — SKIPPED ENTIRELY when step 2 resolved to **Workflow only**: each selected parameter instead gets a minimal record built straight from its raw `params.input` value (semantic name = the raw `Section.Key`, datatype guessed cheaply via `utils.to_number`, unit left unknown/`unit:UNITLESS`), with no LLM client constructed. Otherwise: for candidates not already cached, asks the configured LLM to infer each one's semantic name, datatype, QUDT unit, and quantity kind, using each parameter's own `getParam<Type>()` call-site excerpt (or each metric's own surrounding-code snippet) plus any relevant prior human corrections (`ai.corrections`) as context -- not the full `main.cc`/`problem.hh` source, which used to dominate request size and risk hitting a provider's per-request token/payload limit. Rate-limit safety is layered rather than reactive-only: more than `--inference-batch-size` (default 8) not-yet-cached items are split into multiple independent requests; each resulting chunk is split *again* if its own estimated token cost exceeds `--inference-tpm-budget` (default 9,000), regardless of item count; and every request made during the run reserves its estimated cost against one shared tokens-per-minute budget before sending, so individually-small requests can't collectively exceed it either. Retries up to 3 times before failing (or falling back to a low-confidence placeholder with `--fallback-on-error`) -- except an unrecoverable size/rate-limit response, which fails immediately instead of wasting retries on something that can't succeed; the one exception is a model's *daily* token quota being exhausted, which (by default, disable with `--no-model-fallback`) triggers an automatic switch to a different model this API key can access instead of failing -- see the troubleshooting entry below. Then, parameters and metrics are reviewed in ONE combined pass, not two: on a real terminal, `ai.tui` shows a curses queue -- a summary ("N accepted automatically, M require your review") with four explicit choices -- `[F]` review just the flagged items (confidence below `--review-confidence-threshold`, default `0.7`, or a structural check like a model-omitted `ini`/`key` field reconstructed positionally, or a `quantityKind` backfilled from `unit` alone; or just press Enter), `[A]` also review the N items that were auto-accepted (shown as an option even when nothing was flagged at all, so a clean run still offers the chance to double-check things, not just a "nothing to review" message), `[N]` accept everything without reviewing, `[Q]` quit to the plain-text fallback. Each item in whichever set you chose gets an Accept/Rename/Change unit/Change type/Change quantity kind/Edit explanation action menu -- arrow keys, or a digit, move the highlight to that action right away (visibly, before anything is confirmed), and Enter commits whatever's highlighted, so a stray keypress never fires an action by itself; an item pulled in via `[A]` is labeled "(auto-accepted -- reviewing by request)" in its header, and leaving it as Accept/Skip without editing records a distinct note ("reviewed and accepted (previously auto-accepted)") rather than the low-confidence wording that only applies to actually-flagged rows. A text-editing prompt (e.g. "Edit explanation") starts pre-filled with the field's current value and supports genuine in-place editing rather than a blind retype: Left/Right (also Ctrl-A/Ctrl-E, or Home/End) move the cursor, Backspace/Delete remove a character at a time, typing inserts at the cursor, Enter saves, Esc cancels and leaves the field untouched; text wider than the terminal scrolls horizontally to keep the cursor visible. The prompt text itself is still word-wrapped across as many lines as the terminal's actual width needs, with the editable line always placed on its own row below it, so nothing is clipped -- the same wrapping applies to the Outputs preset descriptions in step 2. Falls back to `ai.review`'s plain-text table per kind whenever curses isn't usable (no real TTY, not importable, or you back out with `q`): type a row number to edit any field, or press Enter to accept the table as shown -- `!`/`?` markers flag rows worth a look, but Enter always accepts either way (every row, flagged or not, is already visible and editable there, so there's no separate accepted-items prompt needed in that fallback). Skipped entirely with `--skip-review` (or, as above, in **Workflow only** mode). Whatever a reviewer changes (either UI) is recorded by `ai.corrections` and offered back to the LLM as guidance for similarly named/typed items in *other* benchmarks.
4. **Build & Generate** (`metadata.builder`, `snakefile.generator`, `snakefile.renderer`) — wraps each reviewed value plus the scraped manifest info into typed nodes inside one metadata4ing `@graph`; author, publisher, and software dependencies are assembled into a *separate* graph (`GraphBuilder.build_dataset_graph()`), not merged into the same one. Checks the benchmark graph against the RO-Crate 1.1 profile, then writes `<benchmark-name>_benchmark.jsonld`, plus whichever of a sidecar `<benchmark-name>_dataset.jsonld` (linked back via `schema:isPartOf`) and a plain `Snakefile` the Select-outputs step above chose, to `outputs/<software-name>/`. In **Workflow only** mode, this builds only a minimal in-memory graph (case-varying parameter values plus a bare `local:software`/`./` node pair) that's never written out as a real deliverable, feeds only `snakefile.generator`, and skips RO-Crate validation entirely (no `benchmark.jsonld` exists to validate) -- `outputs/<software-name>/Snakefile` is the only file produced.

Review and verify the result downstream of generation -- run individually, or (for `show_description.py`) called in-process by `describe_benchmark.py` itself whenever `review.md` is included in the Outputs selection (i.e. every preset except **Workflow only** -- `workflow.py` skips both this and `verify_description.py` for that mode, printing why, since there's no `benchmark.jsonld` to feed either one):

- `show_description.py <benchmark-name>_benchmark.jsonld` auto-discovers the sibling `_dataset.jsonld` file next to it and renders both together as Markdown tables — including manifest fields (license, authors, dependencies) and resolved case values the interactive review step doesn't cover — saved to `review.md` as a durable record, and printed to the terminal too when run this way (directly). Called in-process by `describe_benchmark.py`/`workflow.py` (as above), it's passed `--quiet` so the table is still saved to `review.md` but not also echoed to the terminal on top of it -- both callers already list `review.md` among the generated files right afterward, so printing the whole table inline (potentially twice, once per caller) was mostly noise; pass `--quiet` yourself, or drop it, when calling `show_description.run()`/the CLI directly. Without a dataset sidecar (the "Description only"/"Snakefile" Outputs presets), those manifest sections are simply omitted -- the report still covers the benchmark's own input parameters and output metrics.
- `verify_description.py <benchmark-name>_benchmark.jsonld` loads it with the real `semantic_benchmark.BenchmarkLoader` and confirms every parameter set and metric field mapping resolves (the dataset sidecar isn't involved in this check).

To fix a value after the fact (e.g. a `--skip-review` run, or something spotted later in `review.md`): edit the relevant entry in `.parameter_metadata_cache.json` (or `.metric_metadata_cache.json`) inside the module directory, re-run `describe_benchmark.py` **without** `--clear-cache` so the fix is reused, then re-run `verify_description.py` to confirm.

## Repository layout

- `describe_benchmark.py` — entry point; orchestrates metadata + Snakefile generation.
- `show_description.py` — renders the benchmark file (merged with its sibling dataset file) as Markdown.
- `verify_description.py` — validates the benchmark jsonld file against `semantic_benchmark`.
- `workflow.py` — runs the scripts above as one CI-friendly pipeline.
- `config.py` — optional `--config` YAML support, shared by `workflow.py` and `describe_benchmark.py`.
- `utils.py` — shared string/number/file helpers.
- `metadata/` — `builder.py`, `graph.py`, `repo_source.py` (resolves `module_dir`: local path, or clone/update a git URL), `repository.py`, `parameters.py`, `metrics.py`, `publication.py`, `software.py` — benchmark.jsonld generation.
- `ai/` — `prompts.py`, `inference.py`, `validation.py`, `review.py` (combined review/edit step, run between inference and graph-build; plain-text UI + the shared field-edit logic), `tui.py` (optional curses UI for the parameter selector, the review queue, and the Outputs-step picker, falls back to `review.py`/`metadata.builder`'s plain-text prompts automatically), `cache.py` (inference caching plus the Outputs-step selection persisted to `.benchmantic_outputs.json`), `corrections.py` — LLM-based semantic metadata inference and its cross-benchmark corrections memory.
- `snakefile/` — `generator.py`, `renderer.py` — executable-workflow generation.

## Common edge cases

- **No `--scenario-params` supplied**: falls back to an interactive prompt; unattended/CI runs must pass this flag explicitly or the run will hang waiting for input.
- **No `--skip-review`**: the review step also needs a real terminal (`input()`); unattended/CI runs must pass `--skip-review` or the run will hang there too, even with `--scenario-params` set.
- **Missing required Snakefile flags**: `--container-image` and `--container-shared-dir` are required even if you only care about the `benchmark.jsonld` output.
- **Verification failures**: a failing `verify_description.py` run should block downstream packaging/publishing — `workflow.py` already propagates this as a non-zero exit code.
- **Rotating-cylinder / radial-mesh benchmarks**: only enable `--mesh-split` (and its `--radial-cells-flag`/`--angular-cells-flag`/`--grading-flag`) when the benchmark actually uses a radial mesh; it's not a general-purpose flag.
- **Missing API key**: `GROQ_API_KEY` (or `OPENAI_API_KEY` with `--provider openai`) must be set before the inference step runs.
- **Still hitting rate limits despite `--inference-tpm-budget`**: set it well BELOW your account's actual TPM cap, not equal to it -- e.g. 8,000-9,000 on a 12,000 TPM account. Token estimation is a heuristic (chars/4 plus a per-item completion guess, see `ai.inference`'s `CHARS_PER_TOKEN_ESTIMATE`), and other activity sharing the same API key (a concurrent run, manual testing) eats into the same rolling window that budget is meant to protect.
- **A run says a model "has hit its tokens-per-day quota"**: this is Groq's TPD limit (separate from the per-minute TPM budget `--inference-tpm-budget` targets), tracked *per model*, not account-wide -- confirmed by Groq's own per-model rate-limit table, and consistent with different models on the same account already having very different TPM caps (see `PROVIDER_CONFIG`'s comment in `ai.inference`). By default `ai.inference` handles this automatically: it asks the provider what other models this key can access (`client.models.list()`) and switches to one it hasn't already exhausted, remembering that switch for the rest of the run (parameter and metric inference both) -- so seeing this message in the log doesn't necessarily mean the run stopped, only that one model ran out and another took over; watch for the follow-up "switching to '<model>' for the rest of this run" line (which also names any underlying model Groq's own error blamed, if different from the one requested -- Groq's "compound"/"compound-mini" wrappers can report a TPD error against the model they delegated to internally rather than their own id, and both get excluded from the next pick so fallback doesn't just land on a different wrapper hitting the same underlying exhaustion). The run only actually stops once every reachable model has been tried, and the resulting error names all of them plus the exact wait the last one reported. Pass `--no-model-fallback` to disable this and fail on the very first exhausted model instead (useful if you specifically need output from one named `--model`). Either way: re-running the same command later picks up right where it left off, since already-cached parameters/metrics aren't re-queried; `--provider openai` (with `OPENAI_API_KEY` set) routes around Groq entirely for the rest of the run, and `--fallback-on-error` fills any still-uninferred items with a low-confidence placeholder instead of stopping, to fix by hand in review. Model discovery tries a short curated list of known-good general-purpose models first (`llama-3.3-70b-versatile`, `groq/compound-mini`, `groq/compound`, and a few others -- whichever the account actually has), falling back to a general-purpose-before-small/specialized heuristic ranking only for accounts or providers without any of those. Several more failure modes also trigger an automatic switch, not just quota exhaustion -- all printed as `'<model>' ... can't handle this request ... switching to '<model>'` (or, for JSON-output failures, `produced unusable output on all N attempts ... switching to '<model>'`): a model producing invalid JSON (or JSON that fails schema validation) on all 3 attempts, since retrying the identical request at `temperature=0` can't change the outcome; a model that doesn't exist or isn't enabled for this key (404); a model that needs an org admin to accept its terms first (seen in practice: a TTS model, "canopylabs/orpheus-arabic-saudi", that Groq's own catalog listed right alongside chat models); a single request whose estimated cost exceeds a model's ENTIRE per-minute budget; and 413 request_too_large, a flat payload-size cap smaller than the request needs (seen in practice: switching from 'groq/compound-mini' to its sibling 'groq/compound' for a TPD reason landed on a model with a smaller cap that rejected the identical prompt outright). All but the JSON-output case fail fast on the very first attempt rather than wasting all 3 retries on an identical rejection.
- **A run uses a different model than expected**: `--model` always overrides `PROVIDER_CONFIG[provider]["default_model"]` -- check the actual command/script invocation (and any wrapper/CI job) for a lingering `--model` flag before assuming the default changed. The codebase has exactly one place that sets each provider's default (`ai.inference.PROVIDER_CONFIG`); nothing else in this repo hardcodes or overrides a model name.
- **`quantityKind` missing after inference**: `ai.validation` tries to backfill it from the item's `unit` alone via two live lookups, in order: first the unit's own [QUDT vocabulary entry](http://qudt.org/vocab/unit/) (e.g. `unit:PA` -> `http://qudt.org/vocab/unit/PA`), then, only if that misses, a best-effort fetch of the [SI Digital Framework units page](https://si-digital-framework.org/SI/units?lang=en). Both are defensive by design -- any failure (network, timeout, parse miss) is silently treated as "couldn't determine it," never raised, so neither can break a run; if neither is reachable, the backfill is simply skipped. A successful backfill (either layer) sets `_needs_verification` and shows up as a `?` row in review; an item still left with no `quantityKind` after both layers just stays that way, unflagged beyond the missing field itself. `unit:UNITLESS` is deliberately never guessed (too ambiguous -- Count, DimensionlessRatio, etc. all use it), nor is any item with `datatype: schema:String`.
- **Parameter selection / review / outputs picker look like plain-text prompts, not the curses screens**: `ai.tui` only takes over when both stdin and stdout are a real TTY and the `curses` module imports successfully -- piped output, a CI runner, this doc's own test tooling, or a bare Windows install without `windows-curses` will all silently fall back to the plain-text equivalents (still fully interactive, just not arrow-key-driven). This is automatic and never an error; nothing needs to be passed to opt out or in.
- **A curses screen seems unresponsive to arrow keys, or an action menu doesn't seem to register a choice**: every menu with 9 or fewer options (the review queue's action menu, the datatype picker, the Outputs preset menu) also accepts a plain digit press (`1`-`9`, shown next to each option) that moves the highlight straight to it, immediately and visibly, without depending on arrow-key escape sequences at all -- use that if arrows feel unreliable over a laggy connection (SSH, tmux). The digit only moves the highlight, though; press Enter to actually confirm the highlighted option (a stray digit or arrow press never fires an action by itself). `ai.tui` also lowers ncurses' `ESCDELAY` (the time it waits after a bare Escape byte to see if more bytes belonging to an arrow/function key are coming) from its 1000ms default to 25ms specifically so those sequences don't get partially dropped in the first place.
- **A checklist (parameter selection, the Outputs Custom screen) has more than 9 rows and a digit press doesn't seem to reach the one you want**: these longer lists use a typed number instead of a single keypress -- type the row's own number (shown next to it, works for any row, not just the first 9); the highlight jumps live to that row as each digit lands, and the digits you've typed so far are always visible on their own "Go to #: " line with a real cursor, so you can see exactly what's registered. Press Enter to jump to (and toggle) the highlighted row; Backspace edits the number before you commit it, and `q`/Escape clears a half-typed number rather than cancelling the whole screen. `Space` still toggles the currently highlighted row in one keypress if you're already on it via the arrow keys.
- **The checklist's controls legend looks cut off on a narrower terminal, or you're not sure where a piece of it is**: the movement legend (`↑/↓: move, space: toggle, type a number: to jump`) is a single line right under the title/subtitle, at the top, so it's the first thing visible rather than something to scroll past a long list to find. State that changes as you interact -- the running "N/M selected" count, the "Go to #:" buffer, and the less-frequently-needed `a`/`n`/`q` shortcuts -- prints right after the list instead, near where you're already looking once you've scanned through it. Each line is independently word-wrapped to the terminal's actual width -- an option's own text is never what gets clipped, it just spills onto another line if it doesn't fit on one. The list itself shrinks to make room for however many lines the top and bottom legends need at the current width.
- **A menu (the review action menu, the datatype picker, the Outputs preset menu) showed overlapping or repeated fragments of text, especially after resizing the terminal window**: every curses screen in `ai.tui` fully erases and redraws itself -- title, item panel, and menu together -- on every single frame, not just the parts that changed, specifically so a mid-screen resize (which changes how the wrapped text lines up) can't leave stale characters from the old width sitting underneath the new layout. If this is ever seen again on the latest version, it's worth reporting with the terminal size (`echo $COLUMNS x $LINES`) at the time.
- **Getting asked to choose outputs on every run**: this only happens without `--outputs` and without `--skip-review`. It's not re-asked once a choice for that module exists (`.benchmantic_outputs.json`, written after the very first resolution either way) -- either pass `--outputs <preset-or-list>` every time for a fully non-interactive choice, or just answer once; the saved choice is reused silently on every subsequent run against the same `module_dir` until you delete that file, pass `--outputs` to override it, or answer the prompt differently.
- **`module_dir` as a git URL**: cloned into a throwaway temp directory by default, deleted once the run finishes -- nothing persists across runs, including the per-module inference cache, so each run against the same URL re-infers from scratch. Pass `--keep-clone` if you'd rather clone into a persistent cache directory and reuse it (fetch + checkout, not a full re-clone) -- and its `.parameter_metadata_cache.json`/`.metric_metadata_cache.json` -- on the next run against the same URL. Use `--fresh-clone` to discard and re-clone a persistent one if it ever gets into a bad state.
- **A long line (a field-edit prompt showing a long current value, an Outputs preset description) looked cut off on a non-maximized terminal**: `ai.tui` word-wraps both to fit the terminal's actual width (`_wrap_text()`, used by `_text_input()` and the Outputs preset menu) instead of clipping to one line -- resize the terminal and the next screen redraw re-wraps to the new width automatically, no restart needed.
